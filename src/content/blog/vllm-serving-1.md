## 배경

Platform 에서 vLLM serving runtime 을 지원함에 따라 GPU 자원을 할당받고 동작시키는 것을 잘 이해하는 것이 필요했다. 특히나 폐쇄망 환경에서 GPU 를 물려서 동작시키려면 모델 마다의 동작도 필요하겠지만 최소 구현의 굵직한 부분에서 터지지 않는(?) 선을 골라 사용자가 잘 입력해야했고 제공하는 입장에서도 가이드를 주는 것이 편의성을 높히기 위한 중요 대목이라고 생각했다. 물론 LLM recipe 같은 훌륭한 사이트가 있어서 그걸 폐쇄망 환경에서 잘 제공하는게 나을지 모른다. 그래도 폐쇄망인 만큼 "자원사용을 최소로", "자원은 괜찮은데 성능이 ~~ 이상으로" 등의 조건에 반응하는 matching 이 가능하다면 편리하지 않을까? 그런 고로 익히 들어왔던 LLM serving 의 여러 중요 요소들을 파악해보고 실제 코드 구현에서는 어떻게 동작하고 있는지 등을 정리해서 각 요소마다의 이해도를 높이는 측면에서 조사해보고자 한다.

## 주요 컴포턴트 들의 조사

최근 폐쇄망 환경에 LLM 을 올린적이 있는데, 모델 사이즈가 제법 컸다 (압축파일만 얼추 360G?). 그래서 초기화 하는데 제법 많이 시간이 들 것이라고 생각해 몇번 삽질해서 에러나면 오늘 하루 공치겠거니 싶었다. 하지만 실제로 모델을 올려보면서 느낀점은 Multi-node, Multi-gpu 스케일로 올리는게 아니라면 초기화하는데 아주 오랜시간이 걸리는 것 같지는 않았다. 오히려 가용 자원을 확인하고 GPU 6장에 병렬로 올리려다 보니 "16의 공약수가 아닌 숫자는 병렬로 올려줄수가 없어" 같은 에러를 만났고 그냥 4로 세팅 해서 띄우는 정도로 만족하게 되었다. 그 와중에 학습된 모델의 방식(MoE 같은)에 따른 에러도 좀 뜨고 했던거 같은데, 폐쇄망이라 막 기억이 선명하지는 않다. 이것들과 세간에 알려진 것들을 고려해서 주요 컴포넌트를 한번 나열해보자면

- 모델의 구성 및 학습한 방식에 따른 차이
- 병렬화의 방식 및 종류 (특히 왜 16의 공약수만 N빵이 되는건지 궁금했다.)
- 제일 유명한 KV cache 의 동작과 방식

정도를 먼저 정하고 하나씩 확인해보려고 한다.
